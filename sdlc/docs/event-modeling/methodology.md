# Event Modeling Methodology

Following Martin Dilger's "Understanding Eventsourcing" approach.

## Core Principle

**"Not losing information" is foundational.**

Store what happened (events), not just current state. Events are immutable facts that can be replayed, analyzed, and projected in many ways.

## The Four Patterns

Every event-sourced system uses these four patterns:

### 1. State Change Pattern
```
Command → Event
```

The ONLY way to modify system state.

- **Command**: Intent to do something (imperative, present tense)
- **Event**: Fact that something happened (past tense)

Example:
```
TransferMoney → MoneyTransferred
```

### 2. State View Pattern
```
Events → Read Model
```

Query stored events to build projections.

- **Events**: Source of truth
- **Read Model**: Optimized view for specific queries

Example:
```
[AccountOpened, MoneyDeposited, MoneyWithdrawn] → AccountBalance
```

### 3. Automation Pattern
```
Event → Process → Command → Event
```

Background work triggered by events.

- **Trigger Event**: Starts the automation
- **Process**: Business logic that decides what to do
- **Resulting Command**: New intent generated by automation

Example:
```
OrderPlaced → InventoryCheck → ReserveInventory → InventoryReserved
```

### 4. Translation Pattern
```
External Data → Internal Event
```

Anti-corruption layer for external integrations.

- **External Data**: Data from outside the system
- **Translation**: Converts to domain events
- **Internal Event**: Clean domain representation

Example:
```
PayPalWebhook → PaymentReceivedFromPayPal
```

## Event Design

### Naming Rules

Events must be:
- **Past tense**: Something that HAS happened
- **Business language**: Domain experts understand them
- **Immutable facts**: Never change or delete

Good:
- `UserRegistered`
- `OrderPlaced`
- `PaymentReceived`
- `ShipmentDispatched`

Bad:
- `RegisterUser` (command, not event)
- `ProcessPayment` (present tense)
- `UserData` (not an event)

### Event Content

Events should contain:
- **What happened**: The core fact
- **When it happened**: Timestamp
- **Who/what caused it**: Correlation ID, user ID
- **Relevant data**: Just enough to understand the event

Example:
```rust
struct OrderPlaced {
    order_id: OrderId,
    customer_id: CustomerId,
    items: Vec<OrderItem>,
    total: Money,
    placed_at: DateTime,
}
```

### Event Granularity

Find the right level of detail:

Too coarse:
```
OrderUpdated { order: Order }  // What changed?
```

Too fine:
```
OrderItemQuantityChanged { ... }
OrderItemPriceChanged { ... }
OrderShippingAddressStreetChanged { ... }
```

Just right:
```
OrderPlaced { ... }
OrderItemAdded { ... }
OrderCancelled { ... }
ShippingAddressChanged { ... }
```

## Workflow Design

### Step 1: Identify User Goals

Ask:
- What is the user trying to accomplish?
- What problem are they solving?
- What does success look like?

### Step 2: Brainstorm Events

Use sticky notes (physical or virtual):
- What facts need to be recorded?
- What would we need for auditing?
- What decisions happened?

Don't worry about order yet - just capture everything.

### Step 3: Order Chronologically

Arrange events in typical business process order.

### Step 4: Identify Commands

For each event:
- What triggered it?
- Who issued the command?
- What information was provided?

### Step 5: Design Read Models

For each user need:
- What do they need to see?
- What data is required?
- Which events provide this data?

### Step 6: Find Automations

Look for:
- Events that should trigger other commands
- Background processing needs
- Notifications and integrations

### Step 7: Map Integrations

Identify:
- External data sources
- Translation needs
- Integration events

## Vertical Slices

A vertical slice is:
- A complete user interaction
- From UI through to events
- Independently valuable
- Testable in isolation

Slice structure:
```
[UI Component] → [Command] → [Event(s)] → [Read Model Update] → [UI Update]
```

Good slices:
- "User can place an order"
- "User can view order history"
- "Admin can refund an order"

Bad slices:
- "Set up order database" (technical, no user value)
- "Implement order system" (too broad)

## Information Completeness

Every read model attribute must trace back to an event.

Check:
```
ReadModel.field_x ← Event.data_y
```

If a read model needs data not in any event, either:
1. The event is missing data
2. The read model needs different events
3. Translation is needed

## Summary

1. **Events are facts** - Past tense, immutable, business language
2. **Four patterns** - State change, state view, automation, translation
3. **Vertical slices** - Complete user value, independently testable
4. **Information completeness** - Every read model traces to events
5. **Workflow-first** - Design business process, then implementation
